# CLAUDE.md — agent guide to `sqlite3-sag`

Guidance for an AI agent (or any contributor) working in this repository.
Read this before making changes — several invariants here are load-bearing
and are enforced by CI, not just convention.

## What this repo is

`sqlite3-sag` is the SAG journal as a tamper-evident, SQLite-native
primitive: a declared, append-only log of typed entries with a SHA-256 hash
chain you can `verify()`. It was extracted and generalized from
`project_memory`'s journal core, and given the tamper-evidence that source
never had. It is the reference implementation of a versioned, provider-
neutral protocol (`PROTOCOL.md`, `sag-journal/0.1-draft`).

Three artifacts define the actual contract, in order of authority:

1. **`PROTOCOL.md`** — the wire contract. If code and PROTOCOL.md disagree,
   that is a bug in one of them; PROTOCOL.md's §5/§10 (hash chain, `verify`)
   are FROZEN and must not be casually reinterpreted.
2. **`fixtures/*.json`** + **`sqlite3_sag/conformance.py`** — the frozen,
   machine-checked conformance contract. `tests/test_conformance.py` asserts
   every fixture reproduces byte-for-byte.
3. **`sqlite3_sag/`** — the reference library. `docs/` and `README.md`
   describe it; they are downstream of the code, not the other way around.

## Load-bearing invariants — do not casually change these

- **Register-before-emit fails loud.** An undeclared `kind` passed to
  `remember()` MUST raise `ValueError`, never silently coerce to a default
  kind or drop the entry. See `JournalSchema.validate_kind`
  (`sqlite3_sag/schema.py`) and PROTOCOL.md §3.
- **The hash chain covers `episodes` only — facts are never chained.**
  Facts mutate (supersede/invalidate); a mutable row cannot be part of an
  append-only hash chain without lying about what "append-only" means. See
  `sqlite3_sag/schema.py`'s module docstring and PROTOCOL.md §2. Do not add
  `seq`/`prev_hash`/`row_hash` columns to the `facts` table.
- **BM25 + structural is the floor; dense is optional and NOT wired into
  `SagJournal.recall()`.** `query.py::SagJournal._run` hardcodes
  `dense=None` when calling `declared_core.hybrid_query`. This is
  intentional — see `docs/04-recall.md`. Don't "fix" this by silently
  wiring a dense index into `recall()`; if you add dense support, it needs
  its own opt-in parameter, its own tests, and a ROADMAP.md update, because
  it changes the "$0, no numpy" floor guarantee below.
- **The $0 floor needs no numpy.** `pyproject.toml` declares
  `dependencies = []`; `numpy` is only pulled in by the `dense` extra
  (`declared_core/retrieval/dense.py`, imported lazily *inside* function
  bodies, never at module top level). `tools/verify_standalone.sh` Part B
  proves the hash chain, append/verify, and BM25+structural recall all work
  with numpy uninstalled. Any change that makes numpy importable at module
  load time (a top-level `import numpy`) breaks this floor.
- **`declared_core` owns the retrieval math.** BM25 (`retrieval/bm25.py`),
  structural expansion (`retrieval/structural.py`), RRF/weighted fusion
  (`retrieval/fusion.py`, `retrieval/rrf.py`), intent classification
  (`retrieval/intent.py`), and the rules/dimensions scorer
  (`dimensions/scorer.py`) all live there. `sqlite3_sag` declares its corpus
  (`JournalSchema.corpus_schema()`) and calls `hybrid_query` — it does not
  reimplement ranking. If a ranking bug needs fixing, fix it in
  `declared_core`, not by patching around it in `sqlite3_sag`.
- **`declared_core` is vendored, not a dependency.** It is a byte-identical
  in-repo copy (`VENDORED.json` records its tree hash;
  `tools/revendor.py check` is the drift guard CI runs). Do not hand-edit
  `declared_core/` — a hand-edit will fail the vendoring drift check. If
  `declared_core` needs a fix, fix it in its canonical repo and re-vendor
  with `tools/revendor.py sync --canonical-root <path>`.
- **Do not alter `fixtures/*.json`'s `expected` hashes by hand.** They are
  generated by `tools/gen_fixtures.py` from the reference implementation.
  If a legitimate change to the canonical serialization or hash algorithm
  requires new expected hashes, regenerate them with the tool and let the
  diff show exactly what changed and why — never hand-edit a hex string in
  a fixture file.
- **Do not add a required (non-stdlib) runtime dependency.** The whole
  point of this primitive is that it installs and runs anywhere Python's
  stdlib `sqlite3` does, with `dependencies = []`. A new capability that
  needs a third-party package belongs behind an optional extra (see how
  `dense` is structured in `pyproject.toml`'s `[project.optional-dependencies]`), not in the base install.
- **Idempotency must stay chain-safe.** `remember()`'s `INSERT OR IGNORE` +
  `cur.rowcount == 1` check (`sqlite3_sag/ingest.py`) is what makes a
  duplicate `id` a true no-op — it must not consume a `seq` or advance the
  chain head. If you touch the append path, re-run
  `test_duplicate_id_is_noop_chain_unadvanced` and the `idempotent_reinsert`
  fixture; both exist specifically to catch a regression here.
- **`verify()` walks in `seq` order, never `created_at`.** `created_at` is
  producer-supplied and bound into the hash for tamper-evidence, but it is
  not authoritative for chain order — `seq` is.

## Architecture — read more than one file before changing any of these

- **The append path spans three modules for one reason: one atomic
  transaction.** `ingest.remember()` orchestrates; `chain.py` computes
  `seq`/`prev_hash`/`row_hash`; `payload.py` gates admissibility. All three
  run inside a single `BEGIN IMMEDIATE ... COMMIT` in `ingest.remember` so
  that a duplicate-id no-op, a chained insert, and an optional auto-fact
  either all happen or none do. Reading `ingest.py` alone without `chain.py`
  and `payload.py` will make the transaction shape look arbitrary; it isn't.
- **`JournalSchema` is read by three consumers with different needs:**
  `store.py` uses it for DDL (table/column names), `chain.py` uses it for
  the hash policy (`hash_chain`, `hash_alg`, `ns`), and
  `schema.py::corpus_schema()` compiles it into a `declared_core.CorpusSchema`
  for retrieval. A change to `JournalSchema`'s fields likely touches all
  three call sites — grep before assuming a local edit is complete.
- **The compat shim (`project_memory/__init__.py`) is one file, but its
  correctness depends on the alias assignments living in `schema.py` and
  `query.py`** (`MemorySchema = JournalSchema`, `ProjectMemory = SagJournal`)
  being `is`-identical, not parallel redefinitions. If you ever need a
  divergent behavior for the compat surface, that is a sign the shim's
  design assumption (aliases, not a fork) has been violated — stop and
  reconsider rather than patching around it.
- **The vendoring boundary (`declared_core/`, `VENDORED.json`,
  `tools/revendor.py`) is a supply-chain mechanism, not a copy-paste
  accident.** Read `tools/revendor.py`'s module docstring before touching
  anything under `declared_core/` — it explains why the package is
  duplicated in-tree (byte-identical, standalone install, no PyPI/PYTHONPATH
  coupling) and how the drift guard proves it hasn't been hand-edited.

## What NOT to do

- Do not add a `MemorySchema`/`ProjectMemory` implementation that diverges
  from `JournalSchema`/`SagJournal` — they are aliases by design (chapter 06
  of `docs/`), and consumer code depends on `is`-identity, not just
  duck-typed compatibility.
- Do not backfill a hash chain over pre-existing unchained rows by default.
  PROTOCOL.md §11 is explicit that a retroactive chain cannot prove the past
  and the reference implementation deliberately does not fake it. If you add
  an opt-in backfill tool, it must be clearly labeled as a notarization
  point, not a proof of the past, and it must not become the default
  migration path.
- Do not relax the payload gate's float ban "just for one caller." Floats in
  `metadata` break cross-language canonical-hash parity (chapter 02/03) —
  this is a protocol-level constraint (PROTOCOL.md §5.1, §8), not a style
  preference.
- Do not hardcode a physical table name (`"episodes"`, `"facts"`) into the
  hash preimage. The chain is deliberately table-name-agnostic (`GENESIS` is
  flat, not derived from a name) so identical logical inputs hash
  identically across differently-named tables/streams; splice-protection is
  opt-in via `ns`, not implicit in a table name.
- Do not skip `tools/gen_fixtures.py` + `git diff --exit-code fixtures/`
  after any change to `sqlite3_sag/chain.py` or `sqlite3_sag/conformance.py`
  — this is the exact CI step ("Conformance fixtures regenerate no-op") that
  catches silent drift in the canonical serialization.
- Do not add prose to `README.md`/`docs/` you have not run. This repo's own
  documentation discipline (see `docs/05-conformance-and-provider-neutrality.md`
  and the "Verify your build" section at the end of every chapter) is that
  every command shown is a command that was actually executed against this
  checkout.

## Running things

```bash
pytest -q                              # 25 tests: chain, tamper, idempotency, conformance, compat, hmac, migration
python examples/append_and_verify.py   # smoke: append, verify, tamper-detect
python tools/gen_fixtures.py           # regenerate fixtures/*.json; must be a no-op diff on a clean tree
python tools/revendor.py check         # vendoring drift guard for declared_core/
bash tools/verify_standalone.sh        # fresh-venv install + $0-floor (no numpy) + full suite, standalone
```
